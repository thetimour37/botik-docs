## Правила ведения спеки (действуют с 2026-10-15)

Цель: чтобы спека, код, тексты и задачи не расходились, а изменения делались быстро. Принято 2026-10-15 после проверки примера структуры (папка `spec-example/` удалена, пример есть в истории git: коммит `0a3fe8e`).

> **Статус перехода.** Сейчас спека — один большой файл `спецификация_взаимодействия_v2.md`. Правила ниже описывают целевую структуру. Пока файл не разбит, соблюдаем всё, что возможно в нём (номера правил, статусы, ссылки, порядок работы), а разбиение на файлы — отдельная задача.

### 1. Структура
- Спека разбита по небольшим файлам: `blocks/N-name.md` (по блоку), `commands.md`, `parameters.md`, `glossary.md`, `decisions/YYYY-MM-DD-slug.md`, `README.md` (оглавление).
- Имена файлов: короткие, латиницей, **без номера версии**. Версия спеки — в `README.md` и в git-теге, а не в имени файла.
- Один файл блока: шапка (`id`, `title`, `status`, `linear`), краткое резюме (TL;DR, до 5 строк), таблица правил с номерами, схема, 2–3 эталонных диалога, раздел «Связанное», ссылка «← К оглавлению».

### 2. Что хранит спека
- Спека описывает только **что должно быть**. Заметки «как сделано в коде» не копим: допущения, которые нужно подтвердить, оформляем решением в `decisions/`, остальное — в коде.
- **Статусы реализации не ведутся в спеке**: источник — задачи Linear. Заглушки текстов — по маркеру `TBD-Настя` в коде (список в BOT-45).
- **Открытые вопросы** — задачи Linear с меткой «Настя» (не таблицы в спеке). Закрыли задачу — вопрос ушёл из спеки.
- **Схемы** — в самих блоках (mermaid), отдельные файлы схем не ведём.

### 3. Номера и ссылки
- Каждое правило имеет номер `B4-02` (блок 4, правило 2). Номер не меняется при правках и переносах; новые правила получают следующий свободный. На номер ссылаются задачи Linear, комментарии в коде (`# spec: B4-02`) и тесты.
- Все числа и времена — только в `parameters.md` (`P-EVENING-REPLY-MIN`, значение, константа в коде). В блоках — ссылка на параметр, не число. Меняем значение в одном месте и в коде.
- Тексты Насти лежат в `texts.py`; в спеке — только ключ и ссылка, не копия текста.
- Ссылки между файлами спеки — **обычные markdown-ссылки с относительным путём** (`[текст](../parameters.md#окна-ожидания)`), не wikilinks `[[…]]`: так они работают и на GitHub, и в Obsidian. На ссылки из внешних мест (Linear, код, release notes) — полный URL на GitHub.
- Якоря на заголовки используем осторожно (GitHub и Obsidian обрабатывают их по-разному): для устойчивости ссылаемся на файл и указываем номер правила.

### 4. Решения
- Каждое значимое решение — отдельный файл в `decisions/`: что решили, кто и когда, что было раньше, почему, какие правила затрагивает (`affects`). В тексте правил не пишем «решение такого-то от такой-то даты».

### 5. Статусы и согласование
- В шапке файла: `status: черновик | на согласовании у Насти | согласовано`. «На согласовании» вместо значков 🔴 в тексте: так файлы, ждущие Настю, находятся одним поиском.
- Зоны правки: Настя правит тексты и ставит «согласовано»; Тимур — структуру, номера и параметры. Obsidian-git коммитит каждые 10 минут, поэтому не правим один файл одновременно; перед правкой — `git pull`.

### 6. Порядок работы над изменением
1. Прочитать нужный блок спеки и связанные `parameters.md`, `commands.md`, `decisions/`.
2. Изменить спеку (коммит с номером задачи `BOT-N`).
3. Задача в Linear: со ссылками на раздел спеки (см. ниже).
4. Код; в тесте указать номер правила.
5. Тесты (если менялся код), релиз, release note. В release note — строка «Спека: botik-docs@хеш» и коротко, что изменилось в спеке (ссылки на блоки).

### 7. Задачи Linear и ссылки на спеку
- В описании каждой задачи, связанной со спекой, — раздел **«Спека»** со ссылками **на все файлы спеки, к которым относится задача** (блок, `commands.md`, `parameters.md`, `glossary.md`, решения в `decisions/`), номера правил и карточку `tasks/N-*.md`; по клику должно открываться ровно то, что нужно для работы. До окончания переезда (BOT-60), пока блок не перенесён, — ссылка на монолит. Формат ссылки: `https://github.com/thetimour37/botik-docs/blob/main/spec/…` (кириллица в пути кодируется браузером, ссылку брать из адресной строки GitHub).
- Новые задачи создаём сразу со ссылками. Существующие дополняем, когда берём задачу в работу.
- Шаблон описания задачи: что меняется; критерий готовности; блок и номера правил; нужен ли текст Насти; затронутые файлы; раздел «Спека» со ссылками.

### 8. Проверки (перед релизом)
Автоматизированы скриптом `scripts/check-spec.py` (`python scripts/check-spec.py [--botik ПУТЬ]`; пп. 1–5 дают код возврата 1 при ошибках; запрещённые термины пропускаются, пока в `glossary.md` нет раздела о них; матрица «правило → тест» выводится справочно). Проверяется: нет битых ссылок между файлами; номера правил в коде и тестах существуют в спеке; для текущей версии есть `release_notes/vX.Y.Z.md`; в спеке и в `texts.py` нет запрещённых терминов из `glossary.md`; для каждого правила понятно, какой тест его покрывает.

## Файлы новой концепции (по порядку чтения)

1. **`конспект_встречи_пересмотр_концепции.md`** (в `../meetings/`) — главный документ для понимания сдвига концепции: предпосылки пересмотра, новые принципы и цели, полный алгоритм работы по шагам (этапы A–F), таблица из 9 существенных расхождений со старой концепцией, открытые вопросы и идеи в бэклог.
2. **`анализ_новой_концепции.md`** — экспертная оценка новой концепции: сильные стороны, риски, критическая развилка по методологической базе (почему Human Design не подходит), рекомендации до сборки.
3. **`концепт_продукта_v2.md`** — двухчастный документ: часть I — описание продукта для внешней аудитории, часть II — список из 8 пунктов для согласования с Анастасией, от фундаментального к деталям.
4. **`методологический_каркас_v2.md`** — методологическая основа классификации пользовательских запросов. Слой 1: Колесо баланса (8 сфер жизни). Слой 2: Ценности ACT (10 направлений). Механика классификации с примером. Список из 5 пунктов для согласования с Анастасией.
5. **`спецификация_взаимодействия_v2.md`** — **единственный источник истины** по поведению бота, основной технический документ для разработки (обновлено 2026-10-13, BOT-23). Блоки: онбординг, контракт, определение фокуса, ежедневный сбор (с утренним сообщением), вечер, молчание и пауза, недельный цикл (с сессией психолога), месячный срез. Включает таблицу команд со статусами, таблицу расхождений с кодом и открытые задачи для Анастасии (помечены 🔴). В неё влита `схема_дня_v2.md` (перенесена в `../old/spec/`).
   - **`схема_старта_v2.md`**, **`схема_общения_v2.md`** — обзорные схемы (заменили одноимённые HTML). Тексты не дублируют, ссылаются на спецификацию.
6. **`lean_canvas_botik_v2.md`** (в `../product/`) — Lean Canvas продукта, все 9 блоков, актуальная версия с учётом новой концепции.
