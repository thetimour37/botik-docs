# botik-docs — инструкция для AI-сессий

Этот файл — контекст для любой AI-сессии (Claude Code и совместимых), открытой в этой папке. Прочитать перед тем, как опираться на содержимое репозитория.

## Что это за репозиторий

Документация, бэклог и продуктовые материалы проекта **Ботик (Анастасия)** — Telegram-бот для осознанной рефлексии. Код бота — в отдельном репозитории [`botik`](https://github.com/thetimour37/botik), обычно склонированном рядом (`../botik`).

Разделение сделано намеренно: код — для вайб-кодинга и деплоя, этот репозиторий — для планирования, тестирования и обсуждения функционала. Так проще держать чёткую границу между тем, что реально в продакшене, и тем, что ещё прорабатывается.

## ⚠️ Концепция продукта пересмотрена (август 2026)

В августе 2026 концепция продукта была пересмотрена с нуля после 4-месячной паузы. **`spec/` отражает новую концепцию и сейчас приоритетнее корневых файлов.** `how-it-should-work-backlog.md`, `roadmap.md` и `how-it-works-now.md` в корне отражают **старую** (апрельскую 2026) концепцию и больше не пополняются — единственный оставшийся актуальным пункт (1.5) перенесён в `backlog.md`. Подробности и порядок чтения — в `spec/README.md`.

**Задачи на реализацию новой концепции — в `backlog.md` (корень репозитория), рабочая доска — в `SCRUMBAN.md`.** Это не то же самое, что `spec/`: там продуктовые решения и то, что ещё согласовывается с Анастасией; в `backlog.md` — только то, что уже согласовано и готово к работе (см. §«Задачи на реализацию» в `spec/README.md`).

**Правило нумерации задач (2026-09-14):** сквозная численная нумерация без буквенного префикса исполнителя — `#N` (например `#7`, `#17`). Исполнитель — в поле `@nastya` / `@timur` / `@team`. Legacy-ID (N-*, T-*, TN-*) сохранены в frontmatter карточек `tasks/<N>-<slug>.md` как `legacy_id`. Расширенный контекст задачи (`What / Why / Done when / Notes`) — в этих карточках; `backlog.md` — трассировка и краткое описание.

**Скилл scrumban** (`~/.claude-lab/*/.claude/skills/scrumban/`) применяется **только к проекту Ботик**, доска — `SCRUMBAN.md` в этом репозитории.

## Правило источника истины

**GitHub — источник истины, не локальная копия.** Файлы могли быть изменены не с той машины, откуда ты сейчас работаешь (например, через веб-интерфейс GitHub, другую сессию, или **Jarvis** — AI-ассистент команды с деплой-ключом на запись в этот репозиторий, см. `infra/registry.yaml`, объект `jarvis`). Прежде чем опираться на содержимое любого файла здесь — выполнить `git pull`. Перед push — тоже: конфликт с изменениями от Jarvis реальнее, чем с изменениями с другой машины того же человека.

## Методология разработки (кратко)

Полная версия ведётся в Obsidian вне этого репозитория; здесь — рабочая выжимка, актуальная для AI-сессий.

**Единица работы — цикл**, 1–2 недели. Каждый цикл = одна версия: `v0.1`, `v0.2` … `v1.0` (запуск фан-клуба) → `v2.0` (монетизация). Версии — это **git-теги** на коммитах этого репозитория (плюс GitHub Release для крупных версий), не отдельные папки. Снэпшот состояния на любую версию: `git show vX.Y:путь/к/файлу` или страница релиза на GitHub.

Шаги цикла (операционно — через skill `scrumban`, доска в `SCRUMBAN.md`):
1. **Scope** — задачи без блокера из `backlog.md`, переводятся в `READY`/`IN PROGRESS` на `SCRUMBAN.md` с учётом WIP-лимита.
2. **Build** — реализация по описанию задачи в `backlog.md` и соответствующему разделу `spec/`.
3. **Test** — прогон живьём.
4. **Review** — конспект в `meetings/`.
5. **Ship or Iterate** — задача уходит в `DONE` на `SCRUMBAN.md` (Definition of Done ниже) или возвращается в `backlog.md` с уточнением, почему не зашло.

Большинство задач новой концепции сейчас блокированы ожиданием текстов/материалов от Насти — актуальный список блокеров и что именно запросить смотреть в `SCRUMBAN.md` (секция `BLOCKED`).

**Kanban-статус задачи**: 💡 Идея → 🔴/🟡/🟠/🔵 Бэклог (приоритет) → 🔨 В разработке → 🧪 Тестируется → ✅ Ship → 📊 Измеряется.

**Definition of Done** — задача переходит в ✅ только если: код задеплоен на Railway, прогнана вживую минимум 1 диалоговая сессия, нет новых trust-breaking багов, результат зафиксирован в конспекте встречи. Trust-breaking баг (ломает ощущение, что бот «слышит» пользователя) всегда обгоняет по приоритету новые фичи.

**Версионные гейты**: v0.x — тестирование только с тестировщиком, живая правка багов; v1.0 — все 🔴-задачи закрыты, нет trust-breaking багов → запуск фан-клуба; v1.x — сбор обратной связи, доработка 🟡🟠; v2.0 — продукт стабилен, есть onboarding и хэндофф к психологу → включение монетизации.

## Структура папок и порядок чтения

Для быстрого погружения в проект читать в этом порядке:

1. **`spec/`** (начать с `spec/README.md`) — актуальная (август 2026) переработанная концепция и подробное описание поведения бота, плюс уточнения (`spec/clarifications/`). Сейчас это самый достоверный источник по продукту.
2. **`backlog.md`** — что из `spec/` уже согласовано и готово к реализации, с трассировкой к разделу-источнику. Источник задач для шага Scope.
3. **`SCRUMBAN.md`** — рабочая доска (Backlog/Ready/In Progress/Review/Done/Blocked), тонкий срез из `backlog.md`. Смотреть сюда, чтобы понять, что в работе прямо сейчас и что заблокировано.
4. **`tasks/<N>-<slug>.md`** — расширенные карточки задач (`What / Why / Done when / Notes`), сквозная численная нумерация. `ideas/<N>-<slug>.md` — карточки, переведённые в идеи.
5. **`meetings/`** — конспекты встреч, по одному файлу `конспект_встречи_*.md` на встречу. Смотреть последние по дате для самого свежего контекста и решений — включая встречу о пересмотре концепции.
5. **`product/`** — продуктовые материалы за рамками разработки: lean canvas (обе версии), value proposition canvas, анализ экспертов, видение, примеры оформления. Не нужно для понимания текущей механики бота — только для продуктового/бизнес-контекста.
6. **`how-it-works-now.md` / `how-it-should-work-backlog.md` / `roadmap.md`** — архив старой (апрельской) концепции, не пополняются. Не считать источником задач.

## Синхронизация локальной копии с GitHub

Плагин Obsidian **obsidian-git** настроен на этот репозиторий (`basePath` указывает сюда, а не на весь vault): автопул при открытии Obsidian, автокоммит и автопуш раз в 10 минут. Это основной механизм синхронизации — `scripts/check-sync.ps1` (Windows Task Scheduler) оставлен выключенным как запасной вариант на случай, если плагин отключат.

## Инфраструктура (infra/)

Реестр объектов инфраструктуры (серверы, боты, сервисы, репозитории) — `infra/registry.yaml`, диаграмма — `infra/map.md`. Правило из методологии: **после каждого деплоя, изменения конфигурации сервера/бота или создания нового репозитория — обновить соответствующую карточку в `infra/registry.yaml` (или добавить новую) и пересобрать диаграмму в `infra/map.md`.** Старые объекты не удалять — менять `status` на `archived`. Поле `updated` — всегда текущая дата.

## Что НЕ делать

- Не создавать отдельные папки-версии (`v0.1/`, `v0.2/`) для снэпшотов — версии живут в git-тегах, дублирование ведёт к расхождению копий.
- Не создавать несколько файлов `backlog-v1.md`, `backlog-v2.md`… — бэклог один (`backlog.md`), версии его состояния — те же git-теги, что и у остального репозитория.
- Не переносить содержимое `spec/` целиком в `how-it-works-now.md` — последний должен оставаться сжатым.
- Не заводить задачу в `backlog.md`, пока соответствующий пункт в `spec/` не согласован с Настей (помечен 🔴 «на согласование») — только после согласования.
- Не считать локальную копию актуальной без `git pull`.
