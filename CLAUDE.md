# botik-docs — инструкция для AI-сессий

Этот файл — контекст для любой AI-сессии (Claude Code и совместимых), открытой в этой папке. Прочитать перед тем, как опираться на содержимое репозитория.

## Что это за репозиторий

Документация, бэклог и продуктовые материалы проекта **Ботик (Анастасия)** — Telegram-бот для осознанной рефлексии. Код бота — в отдельном репозитории [`botik`](https://github.com/thetimour37/botik), обычно склонированном рядом (`../botik`).

Разделение сделано намеренно: код — для вайб-кодинга и деплоя, этот репозиторий — для планирования, тестирования и обсуждения функционала. Так проще держать чёткую границу между тем, что реально в продакшене, и тем, что ещё прорабатывается.

## Правило источника истины

**GitHub — источник истины, не локальная копия.** Файлы могли быть изменены не с той машины, откуда ты сейчас работаешь (например, через веб-интерфейс GitHub или другую сессию). Прежде чем опираться на содержимое любого файла здесь — выполнить `git pull`.

## Методология разработки (кратко)

Полная версия ведётся в Obsidian вне этого репозитория; здесь — рабочая выжимка, актуальная для AI-сессий.

**Единица работы — цикл**, 1–2 недели. Каждый цикл = одна версия: `v0.1`, `v0.2` … `v1.0` (запуск фан-клуба) → `v2.0` (монетизация). Версии — это **git-теги** на коммитах этого репозитория (плюс GitHub Release для крупных версий), не отдельные папки. Снэпшот состояния на любую версию: `git show vX.Y:путь/к/файлу` или страница релиза на GitHub.

Шаги цикла:
1. **Scope** — 3–5 задач из верхнего приоритетного блока `how-it-should-work-backlog.md` (сейчас 🔴).
2. **Build** — реализация по `roadmap.md`.
3. **Test** — прогон живьём.
4. **Review** — конспект в `meetings/`.
5. **Ship or Iterate** — задача уходит в ✅ done или возвращается в бэклог с уточнением, почему не зашло.

**Kanban-статус задачи**: 💡 Идея → 🔴/🟡/🟠/🔵 Бэклог (приоритет) → 🔨 В разработке → 🧪 Тестируется → ✅ Ship → 📊 Измеряется.

**Definition of Done** — задача переходит в ✅ только если: код задеплоен на Railway, прогнана вживую минимум 1 диалоговая сессия, нет новых trust-breaking багов, результат зафиксирован в конспекте встречи. Trust-breaking баг (ломает ощущение, что бот «слышит» пользователя) всегда обгоняет по приоритету новые фичи.

**Версионные гейты**: v0.x — тестирование только с тестировщиком, живая правка багов; v1.0 — все 🔴-задачи закрыты, нет trust-breaking багов → запуск фан-клуба; v1.x — сбор обратной связи, доработка 🟡🟠; v2.0 — продукт стабилен, есть onboarding и хэндофф к психологу → включение монетизации.

## Структура папок и порядок чтения

Для быстрого погружения в проект читать в этом порядке:

1. **`how-it-works-now.md`** — как бот работает сейчас, сжатый контекст. Обновляется раз в 2-3 цикла, не после каждой мелочи — если нужны детали свежее, смотреть `spec/`.
2. **`how-it-should-work-backlog.md`** — бэклог: что должно измениться, задачи и приоритеты. Источник истины по приоритетам.
3. **`roadmap.md`** — источник задач конкретно для реализации (формат под Claude Code), обновляется по итогам ревью.
4. **`spec/`** — переработанное, более подробное описание поведения бота и уточнения к нему (`spec/clarifications/` — точечные уточнения по темам). Это сырой материал, из которого компрессируется `how-it-works-now.md`.
5. **`meetings/`** — конспекты встреч, по одному файлу `конспект_встречи_YYYYMMDD.md` на встречу. Смотреть последние по дате для самого свежего контекста и решений.
6. **`product/`** — продуктовые материалы за рамками разработки: lean canvas, value proposition canvas, анализ экспертов, примеры оформления. Не нужно для понимания текущей механики бота — только для продуктового/бизнес-контекста.

```
botik-docs/
├── CLAUDE.md                        — этот файл
├── README.md                        — краткое описание для людей
├── how-it-works-now.md
├── how-it-should-work-backlog.md
├── roadmap.md
├── meetings/
│   └── конспект_встречи_YYYYMMDD.md
├── spec/
│   └── clarifications/
└── product/
```

## Что НЕ делать

- Не создавать отдельные папки-версии (`v0.1/`, `v0.2/`) для снэпшотов — версии живут в git-тегах, дублирование ведёт к расхождению копий.
- Не переносить содержимое `spec/` целиком в `how-it-works-now.md` — последний должен оставаться сжатым.
- Не считать локальную копию актуальной без `git pull`.
